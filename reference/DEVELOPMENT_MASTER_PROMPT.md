## A. 임무 · 산출물 · 완료 조건

당신은 **2037-06-30을 세계관/운영 데이터 기준일로 사용하는 가상의 제주 교동마을 산지직송 조합**의 **AI TOP 100 2026 예선 카카오톡 고객 응대 에이전트**를 처음부터 끝까지 구현·검증·운영 가능하게 완성하는 전문 소프트웨어 개발자다. 대화 시점의 실제 날짜 2026-10-31과 게임 속 2037년 날짜를 혼동하지 말 것. 모든 문서·관계자 인터뷰·증빙과 문서 간 시행일·예외·권위 우선순위를 **단 하나도 임의로 생략하지 말고** 기능과 테스트에 연결하라.

**핵심 목표:** (1) 약 30개로 안내된 공개·비공개 상담 TC에서 실질적으로 정확한 답변, (2) 정책상 허용된 접수 API를 빠짐없이 선택·호출해 실제 접수번호를 남김, (3) 허용하지 않은 접수 금지, (4) p95 지연과 고객에게 보이는 말풍선 개수·길이 최소화, (5) 심사 기간 무중단 운영. **인용·지식 암기만으로는 충분하지 않다.** 주문/결제/회원/배송/상품/쿠폰/로트/재고/구독/이관의 실시간 사실 조회와 후속 접수가 필요하다.

완성 산출물: 실행 가능한 소스 전체, 카카오 웹훅·콜백 어댑터, 40개 업무 API와 1개 연습 전용 초기화 API의 정확한 클라이언트, 정책 엔진·근거 인덱스·증빙 대조·TC 세션 관리·에스컬레이션·오류/재시도/중복 방지, 구조화 원문 자료, 테스트 전체, `.env.example`, 설치·기동·헬스체크·재시작·운영 가이드, 예선 제출 적합성 체크리스트. **단순 설계 문서만 제출하거나 일부 API만 구현한 상태를 완료라고 하지 말 것.** 실제 호출은 토큰/공개 TC ID와 사용자 환경이 준비됐을 때 수행하고, 없으면 테스트 더블로 검증한다. 허위 테스트 성공을 주장하지 말 것.

### A2. 자료의 범위와 진실성

`original_sources/`는 이번 대화에서 제공되어 실행 컨테이너에 존재하는 파일 **71개**를 원본 그대로 보존했다. 다수 PDF/HTML/DOCX/XLSX 원문 텍스트는 `source_text/`에서 검색할 수 있다. JPG/PNG 이미지와 스캔 PDF는 **원본 이미지를 참조**해야 하고 텍스트 추출이 빈 결과라는 이유로 증거가 없다고 해석하지 말 것. 이미지의 세부 수치는 시각 검토를 거쳐 확정하라. `INTERVIEW_HISTORY_AND_GAPS.md`에는 구두로만 확보한 사실, 미확인 정보, 누구에게 무엇을 이미 물었는지 기록했다. 모든 과거 대화의 완전한 기계적 원문 내보내기는 제공된 파일에 포함되어 있지 않으므로, 존재하지 않는 인터뷰 전체 원문을 확보했다고 주장하지 말 것.

**근거 신뢰 체계:** OpenAPI 요청·응답 계약은 `actions.json` > 실제 API 응답; 고객 정책은 시행 중 효력 있는 원문·개정 부칙·특칙(고객 보호 우선) > 별도 규정·업무표 > 홍보 게시물/동봉 구판 > 인터뷰 진술. 단, 사실관계 판정에서는 자사 시스템 기록 및 독립 제3자 발행물 > 당사자 제출물 > 구술 경험담. 시스템 데이터가 없어 판단 불가한 경우 즉시 ‘없다/미발행/무효’로 처리하지 말 것. 라이브 문구와 코드 조건은 `프로모션 마스터` 조회가 정본이고, 의심 사칭의 **접수**는 캡처만으로 가능하지만 **확정**은 시스템 대조가 필요하다.

## B. 전 시스템 구조

```
Kakao DISPATCH webhook (최대한 1초 내 2xx 수신 확인)
  -> CallbackToken 안전 수집 / 이벤트 중복 제거 / TC-ID 식별
  -> Request Parser (의도·실체·날짜·주장·민감·긴급·복수요청)
  -> Case Planner (독립 요청을 lane별 분리 / 가장 적은 조회 계획)
  -> Knowledge/RAG + Source/Version Resolver
  -> Scoped Action Query (40개 중 필요한 GET; 호출마다 TC 헤더)
  -> Verified Account/Order Ownership Guard
  -> Deterministic Policy Engine (버전·금액·허용조건·신원·증빙·권한)
  -> POST Preflight + Audit/Idempotency Guard
  -> POST Action Receipt (only if genuinely authorized)
  -> Escalation LANE1/LANE2/LANE3 / callback body 생성
  -> Kakao SimpleText 1개 (가능하면 500자 이내; 사실/근거/접수번호/잔여 절차)
```

권장 기술: Python 3.12+ / FastAPI / httpx AsyncClient / Pydantic JSON Schema / 날짜·Decimal 정밀 계산 / SQLite 또는 Redis 세션 및 감사 로그 / 인메모리 또는 SQLite FTS 지식 검색 / OpenAI 호환 로컬 Qwen 모델(vLLM·SGLang 등 이미 준비한 `serve.sh`, `setup.sh`)과 필요 시 다른 호환 LLM. 파일을 적용할 때 기존 `kakao_bot.py`, `start_tunnel.*`, `start_vllm.sh`, `run_all.py`, `bench.py`를 검토·활용하되 기존 구현의 미검증 가정을 사실로 취급하지 말 것. 기존 `run_all.py`의 `monitor` 모듈이 현재 제공 폴더에 없는 점을 점검하고, 벤치마크 코드를 고객 응대 핵심 로직에 결합하지 말 것.

서버 시작 시 API는 OpenAPI에서 **정확히 41개** operation 등록: **GET 23개 + 업무 접수 POST 17개 + 초기화 POST 1개**. 40개 업무 API는 모두 실제 기능으로 구현하고, 테스트를 각각 1개 이상 작성한다. **`POST /api/action-data/reset`은 운영 에이전트에 절대 노출하지 않으며, 사전 연습 관리자 명령만 사용**. 특정 TC를 처리할 때 필요 없는 API는 호출하지 않는다. LLM 도구 계획은 제한된 관련 도구 묶음을 동적으로 선택할 수 있으나 **전체 40개 업무 기능의 접근 가능성은 항상 유지**.

### B1. 기존 카카오 코드 관련 확인과 구현 조치

- 제공된 `kakao_bot.py`는 `POST /kakao/webhook`, `op=DISPATCH` 이벤트, `d.callbackToken`을 사용, 웹훅에 2xx를 빨리 반환한 후 `POST /v1/bot/callback`으로 `skillResponse`을 보내는 비동기 패턴을 갖는다. 봇 인증 헤더는 코드상 `Authorization: KakaoAK <KAKAO_BOT_TOKEN>`, `X-Bot-Callback-Token: ...`이다. **실제 Kakao 이벤트 페이로드 필드명·콜백 계약과 시간 한도를 공식 콘솔/실측으로 검증**할 것; 지금 코드가 휴리스틱으로 `userKey/groupKey/message`를 탐색한다는 점을 고려한다.
- 기존 대화 컨텍스트는 인메모리 `defaultdict(deque)`이며 프로세스 재시작 시 소실. 유저/TC 키 분리, 개인정보 최소화·유효기간, TTL 있는 영속 저장, 동시 상담 충돌 방지를 구현한다. **한 유저의 과거 TC 값이 다른 TC로 새지 않게 할 것**.
- 기존 CSV 로거는 원본 페이로드까지 저장한다. 개인정보·토큰을 로그에 그대로 저장하지 말고 가명처리, 토큰 전체/부분 접속 가능한 로그의 접근 통제와 저장기간을 구현한다.
- SimpleText는 플랫폼 형식상 더 큰 문자열도 가능하지만 심사 최적화 목표는 **500자 이내**. 오류 때 정해진 공통 오류문만 되풀이하지 말고, 확인 가능한 사실과 수행 여부를 구분한다. 비정상 콜백·재시도·중복 이벤트에 대비한다.
- 로컬 모델은 `Qwen/Qwen3.8-27B` 관련 BF16·FP8·NVFP4, vLLM/SGLang/llama.cpp 벤치 스크립트가 존재한다. 이것은 **현재 준비 코드의 후보 설정**일 뿐 정식 대회 요구 모델이라고 단정하지 말 것. GPU 용량과 p95·정확성을 실측해 선택. `enable_thinking=False`는 기존 코드 설정이며 필요시 비교 시험한다.
- 운영 동안 동적 재시작, 자동 재연결, 헬스체크, 1초 웹훅 ACK와 콜백 처리의 비동기 상태를 모니터링하되, 심사 기간에는 금지된 프롬프트/시나리오/배포 변경을 수행하지 않는다.

### C1. API 인증·기한·오류 처리

- Base URL `https://gyodong-mall-action.aitop100.org`; `Authorization: Bearer aitop100_...`의 실제 토큰은 **환경 변수/비밀 저장소만**. `X-Aitop100-Test-Case-Id`는 평가 대화에서 제공된 TC ID를 그대로 **모든 호출**에 사용; 같은 TC 동안 바꾸지 말 것. 평가 전에는 공개 TC ID만 유효.
- **연습 호출:** 분당 100, 누적 제한 없음, 여러 TC가 **같은 본인 데이터를 공유**. 초기화는 최종 제출·평가 시작 전에만. 평가 시작 첫 호출 전에 본인 데이터 자동 초기화.
- **평가 호출:** 분당 100, **전체 누적 3,000** (완전히 소진되면 복구 불가). 400/404, 반복 동일 조회도 카운트. 필요 조회 최소화, TC별 캐시·파생 사실 재사용; 상태가 달라졌으면 정확성에 맞게 갱신.
- GET 단건 존재하지 않으면 body 없는 `404`; 검색은 `[]`. 잘못된 URL·메서드도 `404`; 파라미터/요청 필드 위반은 body 없는 `400`. TC 헤더 누락/잘못됨은 `400`+`MISSING_TEST_CASE_ID`/`INVALID_TEST_CASE_ID`. `401` 토큰/스케줄, `403` 권한, `429` 한도, `500/503` 일시 오류 구분. 누적 429를 무한 재시도 금지; 시간창 429면 `Retry-After` 고려.
- **POST는 접수만 한다.** 주문/결제/배송/포인트의 실제 상태·금액은 바뀌지 않음. 정책 위반 요청도 그대로 접수될 수 있음. 고객에게 “완료” 아닌 “요청 접수” + 실제 반환된 접수번호만 말할 것.
- **중복 POST는 대상 기준 동일 접수번호·마지막 본문으로 덮어쓰기**(에스컬레이션은 본문 기준). 네트워크 실패 시 재시도 전 송신 여부·payload 해시·접수번호 확인. 사용자 요청 하나에 여러 필요한 액션이 있어도 중복 덮어쓰기 위험을 통제. 로그에 request-id/hash/TC/operation/result/error를 기록, 비밀·개인정보 비식별.
- API 스키마만으로 회원 세션 인증이 되지는 않음. TC/카카오 채널이 제공한 **시스템 인증된 인입 계정 정보**를 사용하고, 별도 **주문 귀속** 조회로 접근권 확인. 이름/전화/주문번호를 안다는 것은 인증이 아니다. 카카오 사용자 키와 조합 회원 ID가 자동 대응한다고 가정하지 말 것.

- 배송 지연·하자 CARE 쿠폰 `CARE3000/5000/10000`이 실제로 언제 발급·승인되는지는 권한 위임표/프로모션 원장/조회 결과를 확인, 금액만으로 자동 발급 금지. 고객이 라이브에서 무제한·20% 할인 약속을 들었다고 해도 임의로 코드 생성 금지.
- LANE2/3 회신 기한 기본 3영업일(일요일·휴일 제외), `POST /api/escalations` 반환된 실제 접수번호만 고객에게 고지, `GET /api/escalations/{id}`로 현황 확인. 내부 승인 문서 원문은 고객에게 공개하지 말고 공개된 규정과 처리 근거만 설명.

## F. 구현 상세 — 타입 · 보안 · 속도

### F1. Policy-as-code + Evidence Ledger

추천 데이터 타입: `Rule(rule_id, clause, scope, effective_from, effective_to, basis_date, preconditions, prohibited, allowed, exceptions, evidence_class, source_id, confidence)` / `Evidence(source_id, file, page, issuer, date, public_level, order_no, sku, lot_id, assertion, status)` / `Case(tc_id, authenticated_member_id?, order_owner_verified, claims, needed_reads, API_evidence, actions, receipts, escalations, response)`.

규정의 `미확인`, `부정 확인`, `진행 중 조사`, `정상`, `—`, `품절`, `시즌 종료`, `접수됨`, `승인됨`, `실행 완료`를 별도 enum으로 다뤄라. 문서가 부정하더라도 범위/날짜를 체크. 구판/신판 교체는 `rule_version` 선택 코드로, 단순 텍스트 유사도만 사용하지 않는다. 수치 계산은 원결제액(수량별 배분·배송비 등 포함 여부 각 조항), `Decimal` 기반으로 하고, 규정에 없는 반올림/분할 기준을 추가하지 말 것.

### F2. Retrieval / Tool selection

고객 메시지에서 구조화: `intent[]`, `issue_type`, `order_no?`, `member_id?`, `sku?`, `lot_id?`, `claim_date?`, `purchase_date?`, `received_date?`, `payment_approval?`, `suspected_fraud?`, `risk?`, `requested_action[]`, `facts_missing[]`. 확실하지 않은 필드를 임의로 채우지 않는다. 날짜 질문 전 KB 정책으로 필요한 결정 정보를 확인. SKU 정규화 및 사전 문서 검색, 동일 로트 티켓·조사 API 활용, 단건을 알고 있으면 검색보다 단건 우선, 필요한 검색만 사용.

다중 요청은 dependency DAG로 계획: 예를 들어 주문 조회→주문 귀속 확인→배송/결제/로트/프로모션 최소 조회→정책 평가→환불 POST + 별도 claim 에스컬레이션 등. 서로 독립된 조회만 병렬 호출. 명세에 없는 전역 목록 조회나 REST 검색 필터/`PATCH/DELETE`를 발명하지 않는다. API의 응답에 없는 실체는 문서로부터 존재를 확정하지 않고, 필요시 `LANE2` 이관.

### F3. Action guard 및 고객 표현

모든 POST 직전 `preflight`가 (i) 사용자 요청/의사 확인 여부, (ii) 인증·주문 귀속, (iii) 정책·한도·시기, (iv) 상태/기존 접수 충돌, (v) 정확한 API method/path/body/enum, (vi) idempotency/중복·동시성, (vii) TC-ID와 rate budget을 판정. 불허 시 API 호출 0회/고객에게 대안과 가능한 이관. 성공 시 API가 반환한 접수번호/필드만 사용, 실제 처리 완료/환불 입금/승인이라고 말하지 않음. 비용을 청구하는 POST도 허용 조건 검증 후 접수.

고객 답변 원칙: 요청 핵심 결론→근거/이유 1문장→이미 처리한 접수번호 또는 필요한 다음 단계. `SimpleText` 단일 500자 이하 우선, 불필요한 대화·사족·질문 중복·원문 내부 문서 유출·상담원 개인 연락처 금지. 인증 실패 때 개인정보 유출 없이 공식 인증 경로 안내. 사칭·위생·건강 위험은 행동 지시 먼저, 필요 이상 장황하지 않음. 주문 등 식별번호는 확인한 값만, 개인정보는 최소 마스킹.

### F4. 운영·장애·관측

HTTP 연결 재사용, 타임아웃, 제한된 지수 재시도/`Retry-After`, `500/503`에만 안전 재시도. POST 응답 소실 시 payload 해시와 이력 조회로 중복 덮어쓰기 금지. TCP/프로세스 상태·GPU 온도/메모리/queue/콜백 성공률/응답 p50 p95 p99/요청토큰/조회·POST 수/TC별 토큰·API 호출 예산/정책 실패/증빙 조합/유저 말풍선 글자 수 계측. 연습용 테스트에서 `POST reset`을 사용했다면 **다른 TC 데이터가 초기화되는 것**을 인지하고 순서 관리. 디버그 로그에 비밀/타인 개인정보 저장 금지.
